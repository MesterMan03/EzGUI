# EzGUI 3.0 — the macro runtime

EzGUI 2.x generated one function per widget. 3.0 keeps the same public behaviour
(chests, pages, clicks, costs, editor) but the runtime is a small data-driven engine:
menu definitions live in storage, and a handful of macro functions walk them. Adding a
menu, a widget or a state never adds a generated command.

## The one rule everything follows

In 1.21.1 a macro variable is substituted **once, when the function is called**, from
the storage snapshot handed to `function … with storage ezgui:ctx`. A value written
into `ezgui:ctx` *inside* that function is invisible to `$(…)` in the same call.

So every step is split:

| step | file | what it does |
| --- | --- | --- |
| compute | `*_prep`, `load_w`, `state_pick` | writes plain, flat keys (`id`, `comp`, `slot`, `need`, …) into `ctx` |
| print | `emit`, `take_score`, `op_sound`, … | a macro line that only substitutes those keys |
| loop | `draw_loop`, `detect_loop`, `cost_loop`, `act_loop` | recurses with a **fresh** `function … with storage ezgui:ctx` per iteration |

Two consequences that bite:

* A macro refuses to instantiate when a key it prints is **missing** — so
  `core/seed` gives the whole argument surface a default once per entry point.
  It must never run inside a loop, where it would wipe the value being prepared.
* A seeded key is "present", so `execute if data … <key>` is useless to test a
  *value*. Prep files therefore `data remove` a key before writing it conditionally,
  or test the definition (`cost[$(idx)].item`) instead of the flattened copy.

## File map

```

menu/    open, close, page_load, draw (+ draw_loop, draw_cell_loop), place,

api/     open_trigger, close_trigger, last_trigger, save_trigger

```

## Clicks

A widget slot is "clicked" when it no longer holds an item stamped by this pack for
**this menu, this page and this widget id**:

```
execute unless items <container> container.<slot> \
  *[custom_data~{ezgui:{w:1,id:"…",m:<menu>,p:<page>}}] run function ezgui:menu/click
```

Comparing the **stamp** and not the item type is what makes the engine usable in
practice:

* a toggle/progress/cycle redraws in a different state when its score moves — that is
  not a click;
* a page change reuses the same slots for different widgets — that is not a click;
* a picked-up, shift-moved or thrown-out stack *is* a click.

## Painting

* A **full** pass (`ctx.lo = 0`) repaints every cell: page change, handled click,
  editor edit.
* A **partial** pass (`ctx.lo = 1`) only rewrites cells with live text (a score shown
  in the name/lore) or with more than one state. Static cells keep the exact stack the
  client already has — rewriting them every tick makes the client resync its window and
  real clicks get dropped.

## Players and containers

Each player gets a permanent id (`ezgui.pid`), and each open menu is one entity
container tagged `ezgui.cont` + `ezgui.p<pid>`. Diagnostics therefore address the
container by owner, never "the nearest one":

```
data get entity @e[tag=ezgui.cont,tag=ezgui.p12,limit=1] Items
```

## Trigger API

```
/trigger ezgui.open     open the default menu (ezgui:api.default)
/trigger ezgui.close    close
/trigger ezgui.last     reopen the last menu
/trigger ezgui.save     write in-game edits back into the definitions
```

## Tooling

```
cd tools
npx tsx src/cli.ts            # regenerate defs.mcfunction, gen/*, item modifiers
npx tsx src/lint.ts ../data   # the macro rules above, enforced
```

`src/core/guigen.ts` keeps the original guigen core (SNBT emission, item components,
item-modifier live text); `src/core/build.ts` turns a `MenuSpec` into the definition
NBT; `menus/main.ts` holds the real menus that ship with the pack.
